{# partials/timescale_rollup_view_list.html Swapped into #rollup-views-container on page load and again after every "Rebuild Rollups" click (see timescale_rebuild_rollups.html). Context: groups — [{protocol_name, wide_table_name, views: [{view_name, granularity, bucket_interval, status}, ...]}, ...] as returned by services/bridge_service.list_rollup_view_groups. `protocol_name` is "shared_narrow" for the shared narrow-table group; every other group is one wide-table protocol's own hourly/daily/weekly/monthly stack. One checkbox per GROUP, not per view: the finer-grained views within a stack are hierarchically dependent on the coarser ones (weekly is built on daily, daily on hourly, ...), so rebuilding is only ever offered at the whole-stack granularity — see RollupManager.rebuild_all_rollups for why. Checkboxes default checked (rebuild everything unless the admin opts a group out) and are read by triggerRebuildRollups() in timescale_rebuild_rollups.html when the button is pressed — this partial itself makes no request and stages nothing. Each row's `status` is one of: "OK" — view exists and its bucket matches current config (green) "rebuild" — view exists but its bucket no longer matches config (red) "missing" — view does not exist yet (red) Only OK is colored distinctly; "rebuild" and "missing" both render red — either way the row needs attention, and the label text (not color) is what tells the two apart. Styling notes (mirrors timescale_field_checklist.html): - Row text uses paired light/dark classes for the same reason as the Delete Columns checklist — the app is used in both light and dark mode, and a single shade tuned for one background reads as low-contrast on the other. - `w-auto` on is required (not optional) to override mpg.css's global `table { width: 100%; }` rule — see the equivalent note in timescale_field_checklist.html. #}
